# 기차 기반 인벤토리 관리 게임 — 개발 기획서 (MVP)

**문서 버전:** 0.1  
**개발 환경:** Unity / C#  
**기반 프로젝트:** [dope-grid](https://github.com/Full-Metal-Bagel/dope-grid)  
**개발 목적:** 게임의 핵심 플레이 구조를 검증할 수 있는 최소 기능 프로토타입(MVP) 구현

---

## 1. 프로젝트 개요

### 1.1 게임 콘셉트

플레이어가 기차를 타고 여러 도시를 이동하며, 각 도시의 시장에서 아이템을 구매하고 다른 도시에서 판매하는 인벤토리 관리 게임이다.

게임의 핵심 요소는 다음과 같다.

- 제한된 격자 공간에 아이템을 효율적으로 배치한다.
- 도시별 시장에서 기차 인벤토리로 아이템을 이동한다.
- 도시를 이동하면 해당 도시의 시장 인벤토리가 표시된다.
- 아이템은 각각 고유한 가치와 격자 모양을 가진다.
- 특정 아이템끼리 인접하게 배치하면 시너지 효과가 발생한다.

### 1.2 핵심 개발 목표

1. 다양한 크기의 격자형 인벤토리를 생성할 수 있다.
2. 기차와 시장 사이에 아이템을 이동할 수 있다.
3. 아이템을 회전하여 배치할 수 있다.
4. 도시를 이동하면 기차 인벤토리는 유지되고 시장 인벤토리만 교체된다.
5. 아이템별 속성 데이터를 관리할 수 있다.
6. 인접한 아이템의 조합에 따라 시너지 및 가치 변화를 계산할 수 있다.

### 1.3 개발 원칙

- 기존 dope-grid 라이브러리의 기능을 최대한 재사용한다.
- 기존 라이브러리의 내부 코드를 가능한 한 수정하지 않는다.
- 게임 고유 로직은 별도의 C# 스크립트로 구현한다.
- UI와 게임 데이터를 분리한다.
- 향후 아이템 종류, 도시, 인벤토리 형태를 쉽게 추가할 수 있도록 한다.
- 초기 개발에서는 그래픽 완성도보다 정상 동작을 우선한다.

## 2. 게임 화면 구조

### 2.1 기본 화면

게임의 기본 화면은 좌측 기차 인벤토리와 우측 시장 인벤토리로 구성한다.

**좌측: 기차 인벤토리**

- 플레이어가 보유한 아이템을 표시한다.
- 도시를 이동하더라도 아이템의 종류, 위치, 회전 상태는 유지된다.
- 아이템의 이동 및 회전이 가능하다.

**우측: 시장 인벤토리**

- 현재 도시에서 거래할 수 있는 아이템을 표시한다.
- 도시마다 다른 시장 인벤토리를 가진다.
- 기차 인벤토리와 아이템을 주고받을 수 있다.

**그 외 UI**

- 현재 도시 이름
- 다음 도시로 이동하는 버튼 또는 도시 선택 UI
- 현재 보유 자금 및 아이템 가치 표시(후속 단계)

### 2.2 인벤토리 도식

하나의 고정된 인벤토리 크기가 아니라 다양한 격자 형태를 지원해야 한다.

초기 테스트는 기차와 시장 모두 7×6 격자로 진행해도 된다. 단, 해당 크기는 테스트용이며 코드에서 고정하지 않는다.

인벤토리별로 다음 속성을 독립적으로 설정할 수 있어야 한다.

- 가로 격자 수
- 세로 격자 수
- 아이템을 배치할 수 있는 칸
- 아이템이 배치될 수 없는 칸(향후 확장)

초기 MVP에서는 직사각형 인벤토리를 우선 구현하고, 불규칙한 인벤토리 형태는 추가 기능으로 분리한다.

## 3. 핵심 기능 명세

### 3.1 인벤토리 시스템

기존 dope-grid에서 제공하는 격자 관리, 드래그앤드롭, 회전 및 충돌 판정 기능을 활용한다.

**필수 기능**

- 인벤토리에 아이템을 추가하고 제거할 수 있다.
- 아이템을 동일 인벤토리 안에서 이동할 수 있다.
- 두 인벤토리 사이에 아이템을 이동할 수 있다.
- 아이템을 90도 단위로 회전할 수 있다.
- 아이템의 회전 상태에 따라 점유하는 칸이 달라진다.
- 기존 아이템과 겹치거나 인벤토리 범위를 벗어나는 배치를 방지한다.
- 잘못된 배치 시 기존 아이템 위치와 상태가 유지된다.
- 아이템 이동 시 복제나 소실이 발생하지 않아야 한다.

아이템은 1×1, 1×2, 2×2, L자형 등 다양한 모양을 지원해야 한다.

### 3.2 도시 시스템

여러 도시를 정의하고 각 도시마다 독립된 시장 인벤토리를 제공한다.

**초기 구현 예시**

- 도시 A
- 도시 B
- 도시 C

각 도시에는 고유한 도시 ID, 도시 이름, 시장 인벤토리 데이터가 존재한다.

**도시 이동 규칙**

1. 플레이어가 도시 이동 버튼을 누른다.
2. 노선의 이동 비용을 차감한다. 자금이 부족하면 이동이 차단되고 현재 상태가 그대로 남는다.
3. 현재 도시 ID가 변경된다.
4. 기차 인벤토리는 기존 상태 그대로 유지된다.
5. 떠나온 도시의 시장은 테이블의 시작 배치로 되돌아간다.
6. 우측 시장 인벤토리에 새로운 도시의 시장 데이터가 표시된다.
7. 플레이어는 새로운 도시의 시장 아이템을 확인하고 이동할 수 있다.

도시별 시장은 떠나거나 들어갈 때마다 테이블의 시작 배치로 재설정된다. 도시 A에서 아이템을 가져온 뒤 B를 방문하고 다시 A로 돌아오면 A의 시장은 초기 상태로 되돌아 있으며, 기차에 실은 아이템은 그대로다.

도시 이동에는 이동 시간, 연료, 이벤트를 적용하지 않는다. 노선별 이동 비용은 `PuzzleRouteTableData`를 원본으로 구현되어 있다(`Docs/Management/Archive/노선 비용과 시장 초기화 구현 계획.md`).

### 3.3 아이템 데이터 시스템

아이템 종류별로 데이터를 정의하여 저장한다.

Unity의 ScriptableObject 활용을 우선 검토하되, dope-grid에서 사용하는 아이템 데이터 구조와의 호환성을 먼저 확인한다.

**아이템 정의 데이터**

| 필드 | 설명 |
|---|---|
| Item ID | 아이템 종류를 식별하는 고유 ID |
| Name | 아이템 이름 |
| Icon | 아이템 이미지 |
| Base Value | 아이템 기본 가치 |
| Grid Shape | 아이템이 차지하는 격자 모양 |
| Tags | 아이템의 카테고리 및 속성 |
| Synergy Rules | 다른 아이템과의 시너지 규칙 |

**아이템 인스턴스 데이터**

아이템 정의와 별도로 실제 게임에 존재하는 개별 아이템의 상태를 관리한다.

- 인스턴스 고유 ID
- 아이템 종류 ID
- 소속 인벤토리
- 배치 좌표
- 회전 상태

아이템의 기본 정의 데이터는 공유하되, 개별 아이템의 위치나 회전 상태가 다른 아이템에 영향을 주지 않도록 한다.

### 3.4 인접 아이템 시너지

인벤토리 안에서 서로 인접한 아이템 사이의 시너지를 계산한다.

**기본 규칙**

- 상하좌우로 맞닿은 아이템을 인접한 것으로 판정한다.
- 대각선 인접은 초기 버전에서 제외한다.
- 아이템이 여러 격자를 차지하더라도 두 아이템 사이의 인접 관계를 중복 계산하지 않는다.
- 인접 아이템의 태그를 바탕으로 시너지 조건을 판단한다.
- 아이템 이동 또는 회전 시 시너지 효과를 다시 계산한다.

**예시 규칙 (테스트용)**

- 아이템 A의 기본 가치: 100
- 아이템 B의 태그: `Food`
- 아이템 A에 `Food` 태그 인접 시 가치 20% 증가 규칙이 존재
- 두 아이템을 인접 배치하면 A의 최종 가치: 120

이는 시스템 테스트를 위한 예시이며, 실제 아이템 밸런스는 추후 결정한다.

### 3.5 가치 및 경제 시스템

아이템의 가치는 기본 가치와 시너지 효과를 구분하여 계산한다.

기본 계산 예시는 다음과 같다.

`Final Value = Base Value × Synergy Multiplier`

MVP에서는 아이템 가치와 시너지 결과를 화면 또는 디버그 UI에서 확인할 수 있도록 한다.

같은 보드 안의 인벤토리 이동은 무료다. 시장과 기차 사이의 구매·판매는 아이템 소유권 이전과 자금 증감을 한 작업으로 판정하며, 실패하면 아이템·점유·자금을 함께 보존한다.

경제 시스템은 다음 기능을 구현했다.

- 시장에서 구매할 때 자금 차감
- 시장에 판매할 때 자금 증가
- 거래 실패 시 데이터 원상복구
- 도시와 아이템 태그별 구매·판매 비율 차등

구매가는 아이템 가격 테이블의 기본 가치, 판매가는 기차 내 시너지 반영 최종 가치에 도시·태그별 비율을 곱한다. 태그 규칙이 없으면 도시의 명시적 기본 비율을 쓰고, 여러 태그가 맞으면 priority가 가장 높은 규칙 하나를 쓴다. 아이템별 기본 가격은 `PuzzleItemPriceTableData`, 도시별 비율은 `PuzzleTableData.cities`, 시작 자금은 `PuzzleTradeTableData`가 원본이다.

## 4. 권장 소프트웨어 구조

아래 구조는 설계 예시다. 실제 dope-grid API와 프로젝트 파일을 확인한 후 필요한 부분만 조정한다.

| 구성요소 | 담당 역할 |
|---|---|
| Dope-grid | 격자, 아이템 배치, 회전, 충돌 판정, 인벤토리 UI |
| ItemDefinition | 아이템의 정적 데이터 |
| ItemInstance | 아이템 개별 상태 |
| InventoryTransferService | 인벤토리 간 아이템 이동 및 검증 |
| CityDefinition | 도시의 고유 데이터 |
| CityManager | 현재 도시와 도시 전환 관리 |
| MarketInventoryManager | 도시별 시장 데이터 관리 |
| SynergyCalculator | 인접 아이템 시너지 계산 |
| GameManager | 현재 게임 상태와 시스템 연결 |

기존 라이브러리와 게임 로직의 연결은 별도의 어댑터나 서비스를 통해 구현한다.

게임 규칙을 처리하기 위해 불필요하게 기존 라이브러리의 저수준 격자 관리 코드를 수정하지 않는다.

## 5. 단계별 개발 계획

### Phase 1 — 인벤토리 기능 검증

**목표:** 기존 라이브러리로 두 인벤토리 사이의 아이템 이동을 구현한다.

**구현 기능**

- 두 개의 격자형 인벤토리 화면 표시
- 여러 모양의 샘플 아이템 생성
- 같은 인벤토리 안에서 아이템 이동
- 서로 다른 인벤토리 간 이동
- 아이템 회전
- 배치 불가능 위치 판정

**완료 기준**

두 인벤토리 사이에서 아이템을 자유롭게 이동할 수 있고, 회전 및 충돌 판정이 정상 작동한다.

이 단계에서는 도시, 가치, 시너지를 구현하지 않는다.

### Phase 2 — 도시 전환

**목표:** 도시 이동 시 우측 시장 인벤토리만 변경한다.

**구현 기능**

- 도시 3개 정의
- 도시별 시장 데이터
- 도시 이동 버튼
- 도시 전환 시 시장 UI 갱신
- 기차 인벤토리 상태 유지
- 떠난 도시의 시장 시작 배치 재설정
- 노선별 이동 비용과 부족 시 차단

**완료 기준**

도시 A에서 도시 B로 이동했을 때 기차 아이템의 위치 및 회전 상태가 유지되고, 시장 아이템만 바뀐다. 떠난 A의 시장은 시작 배치로 되돌아가며, 노선 비용이 부족하면 이동이 차단된다.

### Phase 3 — 아이템 데이터

**목표:** 아이템 데이터를 개별적인 정의 파일로 관리한다.

**구현 기능**

- ItemDefinition 생성
- ItemInstance 구성
- 아이템별 가치 설정
- 아이템 모양 설정
- 아이템 태그 설정
- 데이터로부터 테스트 아이템 생성

**완료 기준**

새로운 아이템을 추가할 때 기존 코드를 수정하지 않고 데이터 에셋 생성 및 설정만으로 처리할 수 있다.

### Phase 4 — 시너지 시스템

**목표:** 아이템 배치에 따라 최종 가치가 달라지도록 한다.

**구현 기능**

- 인접 아이템 탐색
- 태그 기반 시너지 규칙
- 기본 가치 및 최종 가치 계산
- 아이템 이동·회전 시 재계산
- 가치 변화 확인용 디버그 UI

**완료 기준**

시너지 조건에 해당하는 아이템을 인접 배치하면 가치가 변경되고, 떨어뜨리면 기존 가치로 복원된다.

### Phase 5 — 거래 및 핵심 게임 루프

**목표:** 아이템을 구매하고 도시를 이동해 판매하는 기본 게임 흐름을 완성한다.

**구현 기능**

- 보유 자금
- 구매·판매
- 거래 시 아이템 이동 및 자금 갱신
- 도시별 가격 차이 테스트
- 게임 상태 UI

**완료 기준**

도시 A에서 구매한 아이템을 기차에 적재하고 도시 B로 이동한 뒤 판매하는 일련의 플레이가 가능하다.

## 6. MVP 범위에서 제외할 기능

## 7. AI 코딩 에이전트 작업 지침

이 프로젝트는 AI 코딩 에이전트와 함께 개발한다.

**코드 작성 원칙**

1. 기존 dope-grid 구현 기능을 우선 확인하고 재사용한다.
2. 기존 라이브러리를 수정해야 한다면 그 이유를 설명한다.
3. 요청받은 Phase에 해당하는 기능만 작업한다.
4. 불필요하게 전체 프로젝트를 분석하거나 리팩터링하지 않는다.
5. 기존 API, 클래스 이름 및 파일 구조를 추측하지 않는다.
6. Unity 및 C# 컴파일 오류를 남기지 않도록 한다.
7. 변경 사항을 가능한 한 소수의 파일로 제한한다.
8. 매 단계 완료 후 수정 파일, 주요 기능, 테스트 방법을 간단하게 보고한다.
9. 수정하지 않은 파일의 전체 소스코드는 반복 출력하지 않는다.
10. 원본 라이브러리의 MIT 라이선스 및 저작권 고지를 보존한다.

**AI 토큰 사용량 최소화 원칙**

- 전체 개발을 한 번에 지시하지 않는다.
- 한 단계씩 구현하고 검증한 뒤 다음 단계로 진행한다.
- 파일을 수정하기 전 관련 파일만 확인한다.
- 기존 기능을 다시 구현하지 않는다.
- 기능 구현과 무관한 리팩터링을 금지한다.
- 문제가 발생하면 전체 시스템 재작성보다 원인 분석 및 최소 수정부터 시도한다.

## 8. AI에게 최초로 전달할 작업 요청

이 문서를 전체 프로젝트 요구사항으로 사용한다.

우선 **Phase 1만 구현**한다.

작업 순서는 다음과 같다.

1. 현재 Unity 프로젝트 구조를 확인한다.
2. dope-grid의 인벤토리 및 UI 관련 실제 API를 확인한다.
3. 기존 데모에서 재사용 가능한 부분을 식별한다.
4. 기차와 시장으로 사용할 두 인벤토리를 표시한다.
5. 샘플 아이템을 생성한다.
6. 양쪽 인벤토리 사이의 드래그앤드롭과 아이템 회전을 구현하거나 기존 기능으로 연결한다.
7. 충돌 및 잘못된 배치가 정상 처리되는지 확인한다.
8. 작업 결과와 Unity Editor에서 테스트하는 방법을 보고한다.

기존에 동작하는 기능은 다시 구현하지 않는다.

Phase 1 완료 후 임의로 다음 Phase로 넘어가지 않는다. 작업 완료 기준을 만족했는지 보고하고 해당 단계의 개발을 종료한다.
