# 구매 가격 기본 할증 구현 계획

## 판단과 목표

모든 아이템에 공통으로 적용할 구매 배율을 `PuzzleTradeTableData.json`에 저장하고, 기존 거래 가격 계산에 적용한다. 초기 설정은 `110%`다. 아이템마다 구매가와 판매가를 별도 금액으로 저장하지 않는다.

현재 아이템별 기본 가치는 `PuzzleItemPriceTableData.json`이 소유한다. 도시별 기본·태그 구매/판매 배율은 `PuzzleTableData.cities`가 소유한다. 구매 가격에 공통 할증률을 하나 더 두면 아이템 가격이나 도시 설정을 일일이 고치지 않고 구매 가격의 전반적인 수준을 조정할 수 있다. 별도 구매·판매 금액은 아이템마다 다른 기본 가격이 필요한 규칙이 생겼을 때 검토한다.

이 문서는 구현 계획이며 완료 기록이 아니다. `AGENTS.md`의 테이블 4계층, 씬 로컬 상태, MVP View·Presenter, `Presentation` 표기 규칙을 따른다. 테스트·플레이·검증용 입력이나 캡처·원인 조사 실험은 사용자가 별도로 요청할 때만 수행한다.

## 가격 계산 계약

- 공통 구매 배율은 `PuzzleTradeTableData`의 `purchaseMarkupPercent`로 정의한다. `110`은 기준의 110%, 즉 10% 할증을 뜻한다. 누락·0 이하 값은 테이블 오류다. 코드 기본값이나 폴백을 두지 않는다.
- 구매 가격은 `아이템 기본 가치 × 선택된 도시 구매 배율 / 100 × 공통 구매 배율 / 100`으로 계산한다. 도시 태그 규칙이 없을 때는 해당 도시의 명시적 기본 구매 배율을 쓴다. 여러 태그가 맞으면 기존처럼 우선순위가 가장 높은 규칙 하나를 쓴다.
- 중간 단계에서 반올림하지 않고, 모든 배율을 적용한 최종 금액을 기존 방식대로 가장 가까운 정수로 반올림한다. 정확히 중간인 경우 0에서 멀어지는 방향으로 반올림한다.
- 판매 가격은 현재의 기차 내 시너지 반영 최종 가치와 도시 판매 배율을 사용한다. 턴별 누적 실제 가치와 거래가 연동은 별도의 기획 결정으로 남겨 둔다.
- 예를 들어 기본 가치가 100이고 도시 구매 배율이 120%라면, 공통 구매 배율 110%를 적용한 구매가는 132다. 도시 배율이 100%이면 구매가는 110이다.
- 정수 화폐의 반올림 때문에 기본 가치가 0이거나 낮은 가격의 경우, 할증을 적용해도 정수 구매가가 기존과 같을 수 있다. 이 경우에도 최소 증가액을 별도로 두지 않는다.

## 1단계. 공통 구매 배율 데이터와 검증

**대상** `Assets/Resources/Tables/PuzzleTradeTableData.json`, `GameTables.cs`, `GameTableRules.cs`, `TableManager.cs`.

1. `PuzzleTradeTableData.json`에 `purchaseMarkupPercent`를 추가하고 110을 설정한다. `startingFunds`, 아이템 가격과 도시별 태그 설정은 각 기존 테이블이 계속 소유한다.
2. `PuzzleTradeTableData` DTO에 필드를 추가하고 누락이 정상값으로 위장되지 않도록 검증용 누락 값을 둔다. 가격 비율의 기준 단위는 기존 백분율 표현을 따른다.
3. `GameTableRules`에서 필드 누락·0 이하·계산 가능한 범위를 검증한다. 테이블 오류는 모아서 보고하고 `IsValid`와 `RequireValid()`로 초기화를 차단한다. `TableManager`의 기존 로딩 경로를 사용한다.

**완료 기준** 구매 배율의 원본은 거래 테이블의 단일 필드이며, 누락되거나 유효하지 않은 값으로 게임이 초기화되지 않는다.

## 2단계. 구매 가격 계산과 거래 연결

**대상** `PuzzleInventoryService.cs`, 관련 거래 결과 타입과 가격 표기 코드.

1. 현재 도시·태그에 따른 구매 배율을 기존 `RateFor` 경로로 선택한다. 시장에서 기차로 이동하는 구매에만 테이블의 공통 구매 배율을 추가한다.
2. 기존 `TryGetTradePrice`의 범위 검사와 `decimal` 계산을 확장해 모든 배율을 중간 반올림 없이 적용한다. 곱셈 자체의 `decimal` 오버플로와 `long` 가격 범위 초과를 거래 실패로 처리한다.
3. 드래그 미리보기와 확정 거래가 동일한 `EvaluateDrop` 계산을 사용하게 한다. 놓는 시점에 현재 도시, 원본·대상, 가격과 자금을 다시 확인하고 실패하면 아이템·자금 상태를 보존한다.
4. `GameEvents.TradeInfo`와 기존 분석 기록에는 실제 확정된 최종 거래 가격을 전달한다. 새 분석 필드가 필요하면 `TelemetryPayload`, `Docs/Management/PLAY_LOG.md`와 서버 계약을 함께 갱신한다.

**완료 기준** 모든 도시·태그의 구매 계산에 공통 배율이 적용되고, 미리보기·자금 부족 판정·확정 금액이 같은 계산을 사용한다.

## 3단계. 표시와 문서 정리

**대상** 거래 미리보기·화물 상세·시장 태그 표시 View와 Presenter, `Presentation.cs`, `README.md`, `Docs/Management/TABLES.md`.

1. 예상 구매가와 거래 결과가 할증이 포함된 최종 금액을 표시하게 한다. 기존 상세 화면의 도시 태그 구매 비율은 **도시 배율**임을 구분하고, 공통 구매 배율을 표시한다면 테이블에서 읽어 별도로 표시한다. 문구와 색은 `Presentation`에 둔다.
2. 시장의 `귀함`·`흔함` 표시는 기존 도시 태그의 구매·판매 배율 기준을 따른다. 공통 할증은 해당 분류의 입력에 합산하지 않는다.
3. `README.md`, `Docs/Management/TABLES.md`와 관련 거래 기획 문서에 공통 배율, 가격 계산 순서와 반올림 규칙을 실제 구현에 맞게 반영한다.
4. 사용자 요청 시 기본·태그 배율, 매칭되지 않는 태그, 여러 태그, 낮은 가격의 반올림, 자금 부족과 오버플로, 도시 전환 후 미리보기와 확정 거래를 확인한다. 수행하지 않은 확인을 완료로 기록하지 않는다.

**완료 기준** 구매 금액, 도시 배율 표시, 공통 배율 설정과 거래 결과가 같은 계산 계약을 가리킨다.
