# 노선 비용과 시장 초기화 구현 계획

## 목적과 적용 범위

도시 이동에 노선별 비용을 붙이고, 도시를 떠나면 그 도시의 시장을 테이블 시작 배치로 되돌린다. 이 문서는 확정된 규칙과 처리 계약이며, ⑤만 설계 확정·구현 대기다. `AGENTS.md`의 테이블 4계층, 씬 로컬 상태, 미리 배치한 MVP View, `Presentation`, Input System, `GameEvents` 규칙을 따른다.

## 확정된 규칙

| # | 규칙 | 상태 |
|---|---|---|
| ① | 이동 비용은 **노선(방향)별**이다. `PuzzleRouteTableData.routes`의 `fromCityId`→`toCityId` 행이 원본이고, 반대 방향은 별개 비용이다 | 구현 |
| ② | 비용이 부족하면 **이동이 차단**된다. 패배가 아니라 도시·턴·시장·기차 가치·자금이 모두 그대로다 | 구현 |
| ③ | **비용은 출발 직전, 빚은 도착 후**에 차감한다. 같은 이동에서 비용이 먼저, 빚이 나중이다 | 구현 |
| ④ | **떠난 도시의 시장만** 테이블 시작 배치로 완전 재설정한다(a안). 목적이 아닌 도시는 손대지 않는다 | 구현 |
| ⑤ | 빚(이자) 차감 시 현금이 부족하면 패배 직전까지 **기차 화물을 40% 가격에 강제매각**할 수 있다 | 설계 확정, 구현 대기 |

## 1. 노선 비용

- 원본은 `Assets/Resources/Tables/PuzzleRouteTableData.json`, DTO는 `PuzzleRouteTableData`/`PuzzleRouteData`, 색인은 `TableManager.TryGetRoute`·`HasRoute`, 검증은 `GameTableRules.ValidateRoutes`다.
- `cost`는 0 이상의 정수이며 누락 판별은 다른 테이블과 같은 `-1` 기본값을 쓴다. `from`→`to` 중복, 자기 자신 노선, 미등록 도시 참조, 음수·누락 비용은 항목별로 수집해 보고하고 `RequireValid()`로 초기화를 막는다.
- 순환 이동의 정의는 기존과 같다(시작 도시 우선, ID 오름차순). 맞닿는 두 도시의 양방향 노선이 없으면 테이블 오류로 보고한다. 노선이 없는 상태로 실행되면 `MissingRoute`로 이동만 차단된다.
- 처리는 `PuzzleInventoryService.EvaluateTravel(bool)`과 `Travel(bool)`이 공유한다. `EvaluateTravel`은 `PuzzleTravelResult`를 반환하고 실패 시 아무것도 바꾸지 않는다. `Travel`은 같은 평가를 재사용해 실패 시 그대로 되돌리고, 성공할 때만 아래 순서로 확정한다.

```
1. EvaluateTravel — 진행 상태 → 순환 목적지 → 노선 존재 → Funds >= cost
2. Funds -= cost                         (출발 직전 차감)
3. Train.ApplyTurnValueChange()          (기차 가치 변화)
4. markets[출발 도시] = CreateMarket(…)  (시장 완전 재설정)
5. currentCityIndex / CityMoveCount      (도착·턴 확정)
6. Market.RecalculateValue()
7. NextDebt.moveCount == CityMoveCount 이면 빚 차감(도착 후)
```

- View는 버튼을 누르기 전 `NextRouteCost(bool)`로 목적지 비용을 읽고, `Presentation.PuzzleCityButton`이 `PuzzleCityView`의 이전·다음 버튼 문구에 붙인다(별도 표시 요소 없음 → 씬 수정 불필요). 실패 문구는 `Presentation.PuzzleTravelStatus`가 `PuzzleCityView.ShowTradeStatus`로 표시한다.
- 진행 상태가 종료되면 `NextRouteCost`는 값을 주지 않고 버튼은 이름만 표시한다.

## 2. 시장 완전 재설정(a안)

- `PuzzleInventoryService.CreateMarket(cityId)`가 시장의 유일한 생성 경로다. 기동 때와 떠난 도시를 되돌릴 때 같은 경로를 써서 시작 배치 검증·인스턴스 발급·시너지 스코프(`Market`)가 항상 동일하다.
- `lastInstanceId`는 `Initialize`의 지역 변수에서 **서비스 필드로 승격**됐다. 재설정마다 새 인스턴스 ID를 발급하므로 과거 ID는 재사용하지 않고, 드래그 중이던 구 인스턴스가 살아나는 일이 없다.
- Presenter는 `session.Travel`을 호출하기 전에 `input.CancelCapture()`과 `ClearDrag()`을 이미 수행한다. 재설정 이후 남은 참조로 드래그를 이어잡으려 해도 `EvaluateDrop`의 소속 확인(`source == Train || source == Market`)에서 `InvalidDestination`으로 거부된다.
- View는 매 렌더마다 `session.Market.Placements`에서 그리므로 모델 교체에 상관없이 즉시 반영된다. `MarketCapacity`는 보드 크기 기준이라 변하지 않는다.
- **a안의 대가**: 시작 배치로 되돌리면 이미 사서 기차에 실은 화물이 그 도시 시장에 다시 생긴다(재방문 시 복제). 판매로 줄어든 항목만 제외하는 b안은 채택하지 않았으므로, 밸런스는 노선 비용과 ⑤의 강제매각으로 통제한다.

## 3. ⑤ 이자 부족 시 40% 강제매각 (설계 확정, 구현 대기)

- 현재 `Travel` 7단계에서 `Funds < debt.amount`이면 즉시 `Lost`다. 이를 상태 분기로 바꾼다.
- `PuzzleRunStatus`에 `NeedsLiquidation`(가칭)을 추가한다. 부족하면 패배로 확정하지 않고 이 상태로 진입해 도시·턴·가치 변화·비용 차감은 확정된 채 유지한다.
- 강제매각 가격은 **기존 판매가 기준의 40%**로 정한다(판매 기준 = 이동 직전 기차의 시너지 반영 최종 가치). 도시·태그 비율은 적용하지 않는다. 40%는 `PuzzleTradeTableData.liquidationPercent = 40`로 두어 테이블 원본으로 두고, 누락 판별은 `-1`을 쓴다.
- 화물이 팔리면 매출로 빚을 먼저 갚고(`Funds += price` 후 즉시 `debt`에서 차감) 잔여 빚이 0이면 정상 진행으로 돌아온다. 마지막 빚이면 승리로 판정한다.
- **결정 필요**: 대금을 자금에 먼저 쌓고 플레이어가 `빚 갚기` 버튼을 누르는 방식(버튼 오브젝트 추가 = 씬 수정 필요)과, 매각 즉시 자동으로 빚에 상계하는 방식(기존 UI로 충분). 기본은 후자로 두고 버튼 없이 진행한다.
- `PuzzleRunStatus.Lost`는 강제매각로도 빚을 못 갚고 화물이 모두 남았을 때(또는 플레이어가 종료할 때) 확정한다. 현재는 "남은 화물이 없어 부족"을 판정하는 경로는 신규 구현이 필요하다.
- 추가 작업: `PuzzleInventory`의 강제매각 판정(`EvaluateDrop`의 판매 방향에 `liquidation` 분기), `GameEvents`/`TelemetryEvents`의 `liquidation_sale` 이벤트, `Presentation` 문구, `Docs/TABLES.md`·`Docs/PLAY_LOG.md` 갱신.

## 4. 남은 검증

Play Mode에서 사용자가 확인할 항목이며, 실행하지 않은 항목을 완료로 기록하지 않는다.

- 이전·다음 버튼에 목적지 노선 비용이 표시되고, 자금이 비용보다 적으면 이동이 차단되며 문구만 바뀐다(도시·턴·시장·자금 불변).
- 도시 A에서 시장을 정리한 뒤 B로 이동하면 A는 시작 배치로 되돌아가고, B 시장은 도착 전 상태 그대로다. B를 떠나면 B가 초기화된다.
- 기차는 출발 전과 도착 후의 인스턴스 ID·좌표·회전이 같고, 재설정 후에도 드래그·회전·거래가 정상 동작한다.
- 노선 한 행을 지우거나 비용을 음수로 바꾸면 항목별 테이블 오류가 보고되고 초기화가 차단된다.
- ①~④와 ⑤가 겹치는 2·4·6번째 이동에서 비용 차감 후 자금으로 빚을 갚을 수 있는지, 부족할 때의 동작을 확인한다.
