# 기차 인벤토리 게임 구현 작업 계획

## 목표와 작업 기준

`Docs/기차-인벤토리-관리-게임-기획서.md.md`의 MVP를 현재 Unity 프로젝트에 구현한다. 이 문서는 작업 순서와 완료 기준이며 구현 완료 기록이 아니다. 먼저 평평한 화물과 팔레트 비활성화를 적용한 뒤, 기획서의 Phase 1부터 Phase 5 순서로 진행한다. 사용자가 요청한 단계까지만 구현하고 다음 단계는 별도 요청을 기다린다.

- `AGENTS.md`의 전역 네임스페이스, 씬 로컬 상태, Input System, MVP UI 및 프리팹 규칙을 따른다. 동작·밸런스 데이터는 JSON → DTO → `TableManager` → `GameTableRules`를 사용한다.
- 에이전트가 테스트·플레이·검증용 입력이나 캡처·원인 조사 실험을 수행하려면 사용자의 별도 요청이 필요하다. 아래 완료 기준은 구현 요구사항이며 확인 완료를 뜻하지 않는다.
- 현 프로젝트는 자체 `PuzzleInventory`와 `PuzzleInventoryUI`를 사용하며 `dope-grid` 패키지는 등록되어 있지 않다. 기획서의 라이브러리 재사용 요구를 1단계에서 실제 API와 프로젝트 제약에 비추어 확인하고 적용 범위를 정한다. 외부 패키지 사용 시 해당 라이선스와 저작권 고지를 보존한다.
- `7×6`, 도시 A·B·C, 예시 아이템과 가치·시너지 수치는 초기 개발용 데이터다. 실제 게임 규칙으로 고정하거나 코드·씬에 중복 저장하지 않는다.

## 0단계. 기존 화면을 평평한 화물 인벤토리로 정리

**대상** `Assets/Resources/Tables/PuzzleTableData.json`, `Assets/Scripts/Runtime/Inventory/`, `Assets/Scripts/Runtime/UI/`, `Assets/Scripts/Runtime/Core/Presentation.cs`, `Assets/Art/PuzzleInventoryUI.prefab`, `README.md`, `Docs/TABLES.md`.

1. 기존 조각의 슬롯 좌표와 ID를 유지하면서 모든 방향을 `Flat`으로 바꾸고, 설명에서 홈·돌기 표현을 화물 형태에 맞게 고친다. 슬롯 수·연결성·좌표의 기존 검증을 유지한다.
2. 팔레트의 표시, 입력 히트 판정, 팔레트 반환 삭제를 비활성화한다. 프리팹에서 숨긴 영역도 입력 경로에서 제외하고, View 초기화의 팔레트 필수 참조·용량 검사를 비활성화 상태에 맞게 조정한다. Shift 연결 이동과 관련 안내·강조 표시도 비활성화한다.
3. 빈 보드에서도 기존 이동·회전을 사용할 수 있도록 테이블에 시작 배치를 정의한다. ID, 좌표, 회전과 중복·경계 조건을 항목별로 검증하고 `RequireValid()` 이후 씬 로컬 모델에 한 번만 배치한다. 샘플 수치와 위치의 원본을 테이블에 둔다.
4. 게임 화면에서 샘플 화물을 개별 드래그·회전하고 유효·무효 위치를 구분하도록 기존 View와 Presenter를 연결한다. 팔레트 및 직소 전용 코드는 사용처를 확인하며 후속 인벤토리 전환에 필요한 범위로 정리한다.

**완료 기준** 보드에 평평한 샘플 화물이 표시되고 개별 이동·회전 및 경계·점유 판정을 사용한다. 팔레트와 연결 이동 조작이 비활성화되어 있다.

## 1단계. 두 인벤토리와 무료 이동

**대상** `Packages/manifest.json`, `Assets/Resources/Tables/`, `Assets/Scripts/Runtime/Inventory/`, `Assets/Scripts/Runtime/UI/`, `Assets/Art/`, `Assets/Scenes/Game.unity`.

1. 기획서의 `dope-grid` 저장소와 실제 패키지 버전·API·라이선스를 확인한다. 두 인벤토리 간 이동과 데이터 소유권, 사전 배치 UI·Input System·외부 asmdef 규칙과의 호환성을 조사한다. 사용할 API, 의존성 및 기존 모델과의 경계를 기록하고, 제약과 양립하지 않는 부분은 해결 방식을 명시한다.
2. 기차와 시장을 각각 독립된 크기와 점유 상태를 가진 씬 로컬 인벤토리로 구성한다. 씬 로컬 세션이 모델을 각각 소유하고 Presenter가 대상 모델에 연결되도록 한다. 테이블에서 크기와 시작 배치를 읽고, 샘플로 각각 `7×6`을 설정한다. 프리팹에는 각 보드의 42칸과 최대 점유량을 수용할 배치·고스트·미리보기 요소를 에디터에서 미리 배치한다. 참조 누락이나 용량 부족은 초기화 오류로 처리한다.
3. 아이템 종류와 개별 인스턴스를 구분한다. 인스턴스 ID는 두 인벤토리 전체에서 유일하며 보드 간 이동 후에도 유지한다. 시작 시 중복되지 않는 ID를 발급하고, 종류·소속·위치·회전은 각 인스턴스의 상태로 관리한다.
4. 같은 보드의 이동과 양방향 보드 간 이동을 연결한다. 드래그 시작 시 원본 인스턴스·포즈를 고정하고, 대상 보드에서 회전·경계·점유를 판정한다. 놓는 순간 원본과 대상의 현재 상태를 다시 확인하고 둘 다 유효할 때만 소속·점유를 함께 갱신한다. 실패·취소·화면 밖 해제·포커스 이탈 시 원래 상태를 보존한다.
5. 좌측 기차와 우측 시장의 View 및 Presenter를 Game 씬에 연결한다. 팔레트 원본의 무한 생성 대신 시작 배치된 실물 인스턴스를 사용한다. 여러 크기와 ㄴ자 형태를 테이블로 제공한다.

**완료 기준** 두 독립 보드에서 아이템을 이동·회전하고 양방향으로 옮길 수 있다. 잘못된 이동은 원상태를 보존하며 아이템이 복제되거나 사라지지 않는다. 도시·가치·시너지는 다음 단계에서 연결한다.

### dope-grid 적용 범위

- 공개 릴리스는 Dope Grid 1.2.2와 Dope Inventory (uGUI) 1.0.0이다. 두 패키지는 Unity 2022.3을 최소 버전으로 선언하며, uGUI 패키지는 Dope Grid 1.0.0과 `com.unity.ugui` 1.0.0을 의존성으로 선언한다. 저장소는 Full-Metal-Bagel의 MIT 라이선스를 사용한다. [릴리스](https://github.com/Full-Metal-Bagel/dope-grid/releases) · [Grid 패키지 선언](https://raw.githubusercontent.com/Full-Metal-Bagel/dope-grid/main/Packages/com.fullmetalbagel.dope-grid/package.json) · [uGUI 패키지 선언](https://raw.githubusercontent.com/Full-Metal-Bagel/dope-grid/main/Packages/com.fullmetalbagel.dope-inventory-ugui/package.json) · [라이선스](https://github.com/Full-Metal-Bagel/dope-grid/blob/main/LICENSE)
- 1.2.2의 `ImmutableGridShape.GetRotatedShape`는 회전된 모양을 반환한다. `IndexedGridBoard.TryAddItemAt`과 `RemoveItem`은 한 보드의 점유를 바꾸며, 제거된 슬롯 ID는 재사용한다. `DefaultGameInventory.TryMoveItem`은 공유 GUID로 보드 간 이동을 처리하지만, 원본을 제거한 뒤 대상 등록이 실패하면 예외를 던지고 원본을 복구하는 경로가 없다. 인스턴스 ID, 소유권과 이동 확정은 씬 로컬 `PuzzleInventory`가 관리한다. [격자 API](https://github.com/Full-Metal-Bagel/dope-grid/blob/c1a0487c7c7d9b389000858da7edff37d47c0296/Packages/com.fullmetalbagel.dope-grid/Runtime/Grid/IndexedGridBoard.cs) · [인벤토리 이동 API](https://github.com/Full-Metal-Bagel/dope-grid/blob/c1a0487c7c7d9b389000858da7edff37d47c0296/Packages/com.fullmetalbagel.dope-grid/Runtime/Inventory/DefaultGameInventory.cs)
- 외부 런타임 asmdef 두 개는 `autoReferenced`다. 격자 asmdef는 Unity.Mathematics를 참조하고 패키지의 `csc.rsp`는 C# 10을 지정한다. 프로젝트의 기본 언어는 C# 9이며 패키지 포함 컴파일은 확인하지 않았다. uGUI의 기본 풀은 정적 풀에서 Image를 런타임에 생성한다. 따라서 1단계는 기존 격자와 Input System, 사전 배치 View를 사용한다. 외부 패키지 의존성은 보류한다. [격자 asmdef](https://github.com/Full-Metal-Bagel/dope-grid/blob/c1a0487c7c7d9b389000858da7edff37d47c0296/Packages/com.fullmetalbagel.dope-grid/Runtime/DropGrid.asmdef) · [패키지 컴파일 옵션](https://github.com/Full-Metal-Bagel/dope-grid/blob/c1a0487c7c7d9b389000858da7edff37d47c0296/Packages/com.fullmetalbagel.dope-grid/Runtime/csc.rsp) · [uGUI 기본 풀](https://github.com/Full-Metal-Bagel/dope-grid/blob/c1a0487c7c7d9b389000858da7edff37d47c0296/Packages/com.fullmetalbagel.dope-inventory-ugui/Runtime/Model/DefaultInventoryItemViewPool.cs)

## 2단계. 도시 전환과 시장 상태

**대상** 도시 정의·시장 초기 배치 테이블, 씬 로컬 도시 및 인벤토리 상태, Game 씬의 미리 배치된 도시 표시와 이동 버튼.

1. 도시 ID·이름·시장 크기·초기 아이템 배치를 테이블로 정의하고 ID 중복, 아이템 참조, 배치 충돌과 범위를 검증한다. 세 도시의 샘플을 제공한다.
2. 현재 도시 ID와 도시별 시장 인벤토리를 씬 로컬 상태로 보유한다. 도시 이름 및 선택·이동 순서는 명시적 식별자 또는 경로로 정하고 JSON 배열 순서에 의존하지 않는다.
3. 도시 전환 시 진행 중 드래그를 취소하고 기차 인벤토리를 유지한다. 우측 View를 목적지 시장 상태에 연결하며, **떠난 도시의 시장은 테이블의 시작 배치로 재설정한다**(재방문 시 초기 배치). 도시 전환 버튼은 Input System UI 모듈을 사용한다. 노선별 이동 비용은 출발 직전 차감하고 부족하면 이동을 차단한다(`Docs/노선 비용과 시장 초기화 구현 계획.md`).

**완료 기준** A에서 시장 아이템을 옮긴 뒤 B를 방문하면 A가 시작 배치로 되돌아가고, A로 돌아와도 초기 배치이며, 전환 전후 기차의 인스턴스·좌표·회전이 유지된다. 노선 비용이 부족하면 도시·턴·시장·자금이 그대로 남는다.

## 3단계. 아이템 정의와 개별 상태

**대상** 아이템 테이블 및 DTO·인덱스·검증, 인벤토리 모델, `Presentation`, 미리 배치된 아이템 표시 참조.

1. 아이템 정의에 ID·이름·설명·슬롯 형태·태그와 표시 에셋 참조 키를 두고, 기본 가격은 아이템 ID별 가격 테이블에서 조회한다. 공용 표시 자산은 프리팹에 연결하고 테이블의 ID와 참조를 검증한다. 슬롯 배열 순서에 의미를 두지 않는다.
2. Phase 1의 실물 인스턴스에 종류 ID·소속·좌표·회전 상태를 연결하고, 같은 종류의 서로 다른 인스턴스가 독립적으로 이동하도록 한다. 정의 데이터는 공유하고 실행 상태는 씬 로컬 모델이 보유한다.
3. 테이블에 새 정의와 시작 배치를 추가하면 코드 수정 없이 표시·배치할 수 있도록 기존 로딩과 검증 경로를 연결한다. 실제 아이템 목록과 가치는 기획 확정 전 샘플로 표시한다.

**완료 기준** 동일 종류의 여러 인스턴스가 독립적으로 동작하고 새 아이템 정의가 기존 코드 변경 없이 로드된다.

## 4단계. 인접 시너지와 가치 표시

**대상** 시너지 규칙 테이블, `GameTableRules`, 씬 로컬 인벤토리 계산, 미리 배치된 가치 표시 View·Presenter.

1. 상하좌우로 인접한 서로 다른 아이템 쌍을 인스턴스 ID로 식별하고, 여러 슬롯이 맞닿아도 같은 쌍은 한 번만 계산한다. 대각선과 서로 다른 인벤토리의 아이템은 제외한다.
2. 규칙 ID·대상 및 이웃 태그·배율을 테이블에 두고 참조·수치 범위를 검증한다. 복수 규칙 적용 순서와 중복 처리, 기차와 시장 각각의 적용 범위는 기획 확정 후 테이블 계약에 명시한다.
3. 배치·이동·회전·보드 간 이동 및 도시 전환이 확정된 후 영향을 받는 인벤토리의 최종 가치를 계산한다. 기본 가격은 아이템 가격 테이블에서, 최종 가치는 그 가격을 기준으로 계산해 표시한다.

**완료 기준** 조건이 맞는 인접에서 지정된 가치 변화가 나타나고, 분리·회전·이동 후 현재 배치에 맞게 다시 계산된다.

## 5단계. 거래와 게임 흐름

**대상** 아이템 가격 테이블, 도시 거래 설정, 씬 로컬 자금·거래 서비스, Game 씬의 자금·가치·도시 UI.

1. 아이템별 기본 가격을 별도 테이블에 정의하고, 도시별 거래 허용 여부와 기본·태그별 가격 비율은 도시 데이터에 둔다. 가격 누락·중복·미등록 참조와 비율 범위를 검증한다.
2. 거래는 아이템 소유권 이전과 자금 증감을 하나의 작업으로 판정한다. 자금 부족, 배치 실패, 원본 변경 또는 거래 실패 시 아이템·점유·자금을 함께 보존한다.
3. 현재 도시, 보유 자금과 거래 결과를 미리 배치된 View에 표시한다. 필요한 도메인 사건은 `GameEvents`로 발행하고 분석 기록은 기존 `TelemetryRecorder` 계약을 따른다.

**완료 기준** 도시 A에서 구매한 아이템을 기차에 적재하고 도시 B에서 판매할 수 있으며, 실패한 거래는 자금과 아이템 상태를 바꾸지 않는다.

## 단계별 마무리

- 각 단계에서 실제 연결한 씬·프리팹·테이블과 관련 문서만 함께 갱신한다. `README.md`에는 현재 구현과 남은 제약을 짧게 기록한다.
- 사용자가 요청한 단계의 구현과 씬 연결을 마치면 실제 변경과 남은 사항을 보고하고 중단한다. 사용자 요청 시에만 테스트·플레이를 수행하고 그 결과를 기록한다.
